1. CRUD completo de una entidad principal

La entidad principal seleccionada es Pedido, que representa la orden realizada por un cliente en una mesa del restobar. El CRUD completo ha sido implementado mediante la clase PedidoService y el controlador PedidoController.

ReadlistarPedidos(), obtenerPedido()Consulta lista de pedidos con JOIN a mesa y usuario; consulta detalle por ID.
Updateactualizar()Modifica mesa, productos y recalcula total; gestiona cambio de mesa.
Deletecancelar()Desactivacion logica: cambia estado a "cancelado" y libera la mesa.

2. Operaciones Create, Read, Update y Delete o desactivacion

2.1 Create (Registrar)

public function registrar(array $datos): int { $this->validarDatosEntrada($datos); $this->validarMesaDisponible($idMesa); $this->validarProductosDisponibles($productos); // Transaccion: inserta pedido, detalles, actualiza mesa, crea preparacion }

2.2 Read (Consultar)

public function listarPedidos(): array { return $this->pedidoModel->getPedidosConDetalle(); } public function obtenerPedido(int $id): ?array { return $this->pedidoModel->getPedidoPorId($id); }

2.3 Update (Actualizar)

public function actualizar(int $idPedido, array $datos): void { $this->validarPedidoEditable($idPedido); $this->validarMesaDisponible($idMesa, $idPedido); // Transaccion: actualiza pedido, reemplaza detalles, gestiona mesas }

2.4 Delete (Cancelar / Desactivacion logica)

public function cancelar(int $idPedido): void { $this->validarPedidoCancelable($idPedido); // Transaccion: estado = 'cancelado', mesa = 'libre', preparacion = 'cancelado' }

Justificacion de desactivacion logica: Se opto por no eliminar fisicamente los pedidos para mantener el historial de ventas, permitir auditoria y preservar la integridad referencial con las tablas de pago y preparacion.

CUMPLIMIENTO: Las 4 operaciones CRUD funcionan correctamente con transacciones SQL.

private function validarMesaDisponible(int $idMesa, ?int $excluirPedido = null): void { $mesa = $this->mesaModel->find($idMesa); if ($mesa['estado'] === 'ocupada') { throw new RuntimeException('La mesa esta ocupada. Seleccione otra mesa.'); } }

4. Validaciones sintacticas

Las validaciones sintacticas verifican formato, tipo de dato, longitud y campos obligatorios antes de procesar la informacion.

private function validarDatosEntrada(array $datos, bool $esEdicion = false): void { if (empty($datos['id_mesa']) || !is_numeric($datos['id_mesa'])) { throw new InvalidArgumentException('El campo mesa es obligatorio y debe ser numerico.'); } if (empty($datos['id_usuario']) || !is_numeric($datos['id_usuario'])) { throw new InvalidArgumentException('El campo mozo es obligatorio y debe ser numerico.'); } if (empty($datos['productos']) || !is_array($datos['productos'])) { throw new InvalidArgumentException('Debe seleccionar al menos un producto.'); } if (count($datos['productos']) > 20) { throw new InvalidArgumentException('No puede seleccionar mas de 20 productos.'); } }

Ademas, el modelo PedidoModel incluye reglas de validacion de CodeIgniter:

protected $validationRules = [ 'id_mesa' => 'required|is_natural_no_zero', 'id_usuario' => 'required|is_natural_no_zero', 'estado' => 'required|in_list[pendiente,en_preparacion,listo,entregado,cancelado]', 'total' => 'required|decimal', ];
CUMPLIMIENTO: Validaciones sintacticas en Service y Model: campos obligatorios, numericos, arrays y limites.

7. Persistencia separada de la logica de negocio

La arquitectura respeta la separacion de responsabilidades:

CapaResponsabilidadEjemplo
VistaMostrar y capturar informacionformulario.php, consultar.php
ControllerRecibir solicitudes y preparar respuestasPedidoController::registrar()
ServiceAplicar reglas y coordinar operaciones del negocioPedidoService::registrar()
ModelRealizar operaciones de persistenciaPedidoModel::insert()
Base de datosAlmacenar informacion y mantener restriccionesMySQL con InnoDB

El Controller nunca accede directamente a la base de datos; solo delega al Service, quien a su vez utiliza los Models para persistir.

// Controller: solo recibe y responde public function registrar() { try { $idPedido = $this->pedidoService->registrar($datos); return redirect()->to('/pedidos/ver/' . $idPedido) ->with('success', '...'); } catch (Exception $e) { return redirect()->back()->with('error', $e->getMessage()); } }
CUMPLIMIENTO: Persistencia (Model) separada de la logica de negocio (Service).

8. Manejo basico de excepciones

El sistema captura diferentes tipos de excepciones y responde de manera adecuada sin exponer informacion tecnica al usuario.

try { $idPedido = $this->pedidoService->registrar($datos); return redirect()->to('/pedidos/ver/' . $idPedido) ->with('success', 'Pedido registrado correctamente.'); } catch (\InvalidArgumentException $e) { // Error de validacion sintactica return redirect()->back()->withInput()->with('error', $e->getMessage()); } catch (\RuntimeException $e) { // Error de regla de negocio return redirect()->back()->withInput()->with('error', $e->getMessage()); } catch (\Exception $e) { // Error tecnico: se registra en log, mensaje amigable al usuario log_message('error', '[PedidoController::registrar] ' . $e->getMessage()); return redirect()->back()->with('error', 'Ocurrio un error inesperado. Intente nuevamente.'); }

Los errores tecnicos se registran en el log del servidor (writable/logs/) mientras que al usuario se le muestra un mensaje comprensible.

CUMPLIMIENTO: Manejo de 3 niveles de excepciones con mensajes diferenciados para el usuario.

10. Controladores conectados con los servicios

El PedidoController instancia el PedidoService en su constructor y delega todas las operaciones de negocio a el. El controlador nunca accede directamente a los modelos para operaciones complejas.

class PedidoController extends BaseController { protected $pedidoService; public function __construct() { $this->pedidoService = new PedidoService(); } public function registrar() { $idPedido = $this->pedidoService->registrar($datos); } public function actualizar($id) { $this->pedidoService->actualizar((int)$id, $datos); } public function cancelar($id) { $this->pedidoService->cancelar((int)$id); } }
CUMPLIMIENTO: Controlador conectado exclusivamente al Service para todas las operaciones de negocio.

12. Un flujo funcional completo

El flujo funcional completo de extremo a extremo para el caso "Registrar un nuevo pedido" es:

  1. Vista: El mozo accede a /pedidos/nuevo y ve el formulario.
  2. Vista: Selecciona mesa libre, productos y cantidades.
  3. Controller: El formulario POST llega a PedidoController::registrar().
  4. Controller: Extrae los datos y los pasa al Service.
  5. Service: PedidoService::registrar() aplica validaciones sintacticas y semanticas.
  6. Service: Verifica reglas de negocio (mesa libre, productos disponibles).
  7. Service: Inicia transaccion SQL.
  8. Model: Inserta el pedido en la tabla pedido.
  9. Model: Inserta los detalles en detalle_pedido.
  10. Model: Actualiza la mesa a estado "ocupada".
  11. Model: Inserta registro de preparacion en preparacion.
  12. Service: Confirma la transaccion.
  13. Controller: Redirige a /pedidos/ver/{id} con mensaje de exito.
  14. Vista: Muestra el detalle del pedido registrado.

Diagrama del flujo:

Vista (formulario.php) -> POST -> Controller (PedidoController::registrar) -> Service (PedidoService::registrar) -> validaciones sintacticas -> validaciones semanticas / reglas de negocio -> Model (PedidoModel::insert) -> Model (DetallePedidoModel::insert) -> Model (MesaModel::update) -> Model (PreparacionModel::insert) -> transaccion completa -> redirect -> Vista (ver.php) + mensaje flash
CUMPLIMIENTO: Flujo funcional completo de extremo a extremo verificado.

Conclusion

El presente entregable cumple con los 13 requisitos establecidos en la Guia de Laboratorio N. 4. El modulo de pedidos del sistema Sagras Restaurant cuenta con un CRUD completo implementado sobre la entidad principal Pedido, utilizando una arquitectura en capas donde la logica de negocio esta separada de la persistencia mediante la clase PedidoService.
