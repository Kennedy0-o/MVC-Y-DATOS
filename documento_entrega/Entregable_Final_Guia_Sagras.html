1. Proyecto CodeIgniter 4 ejecutable

1.1 Descripción

El proyecto debe ser un sistema desarrollado con el framework CodeIgniter 4, capaz de ejecutarse en un servidor local mediante el comando php spark serve o en un servidor Apache/Nginx con PHP 8.1+.

1.2 Evidencia

El sistema "Sagras Restaurant" fue desarrollado sobre CodeIgniter 4.2+ utilizando la estructura estándar del framework. El punto de entrada es public/index.php y el servidor de desarrollo se levanta con:

$ php spark serve CodeIgniter v4.x Development Server Started Listening on: http://localhost:8080 Document Root: /sagras/public

El proyecto incluye todas las carpetas estándar de CI4: app/, public/, writable/, vendor/ y el archivo spark para comandos de consola.

✓ CUMPLIMIENTO: El proyecto es completamente ejecutable mediante php spark serve y responde correctamente en el puerto 8080.

2. Estructura MVC identificada

2.1 Descripción

La arquitectura Modelo-Vista-Controlador (MVC) debe estar claramente identificada en el código fuente, con separación de responsabilidades entre capas.

2.2 Evidencia de la estructura

CapaCarpetaResponsabilidad
Modelo (Model) app/Models/ Acceso a datos, validaciones, relaciones con la base de datos.
Vista (View) app/Views/ Presentación HTML, formularios, tablas, interfaz de usuario.
Controlador (Controller) app/Controllers/ Lógica de negocio, recepción de peticiones, coordinación entre Modelo y Vista.

2.3 Ejemplo de flujo MVC

Cuando un usuario accede a /pedidos/nuevo:

  1. Ruta redirige a PedidoController::nuevo()
  2. Controlador solicita datos a MesaModel y ProductoModel
  3. Modelo consulta la base de datos y devuelve arrays
  4. Controlador pasa esos arrays a la Vista pedido/registrar.php
  5. Vista renderiza el HTML con los datos recibidos
✓ CUMPLIMIENTO: Las tres capas están físicamente separadas en carpetas distintas y comunican entre sí siguiendo el patrón MVC.

3. Módulos principales documentados

3.1 Descripción

Cada módulo funcional del sistema debe estar documentado, indicando su propósito, archivos involucrados y flujo de trabajo.

3.2 Módulos del sistema Sagras

a) Módulo de Autenticación

Gestiona el acceso de usuarios según su rol (mozo, cocina, gerente). Implementado mediante UsuarioModel y validación de credenciales.

b) Módulo de Gestión de Mesas

Registro, consulta y seguimiento de órdenes. Archivos: PedidoController, PedidoModel, DetallePedidoModel, vistas consultar.php, registrar.php, ver.php.

Visualización del menú organizado por categorías. Archivos: ProductoController, ProductoModel, CategoriaModel, vista producto/consultar.php.

e) Módulo de Preparación (Cocina)

Seguimiento del estado del pedido en cocina. Archivos: PreparacionModel, integrado en el registro de pedidos.

✓ CUMPLIMIENTO: Los 5 módulos principales están identificados, cada uno con sus Modelos, Controladores y Vistas asociados, documentados en el README.md.

4. Ruta, controlador y vista propios

4.1 Descripción

El sistema debe contar con al menos una ruta personalizada, un controlador propio y una vista asociada, demostrando dominio del enrutamiento de CI4.

4.2 Evidencia: Módulo de Pedidos

Rutas definidas en app/Config/Routes.php:

$routes->get('pedidos', 'PedidoController::index'); $routes->get('pedidos/nuevo', 'PedidoController::nuevo'); $routes->post('pedidos/registrar', 'PedidoController::registrar'); $routes->get('pedidos/ver/(:num)', 'PedidoController::ver/$1');

Controlador app/Controllers/PedidoController.php:

class PedidoController extends BaseController { protected $pedidoModel; protected $detalleModel; protected $mesaModel; protected $productoModel; public function __construct() { $this->pedidoModel = new PedidoModel(); $this->detalleModel = new DetallePedidoModel(); $this->mesaModel = new MesaModel(); $this->productoModel = new ProductoModel(); } public function index() { $data['pedidos'] = $this->pedidoModel->getPedidosConDetalle(); $data['titulo'] = 'Listado de Pedidos - Sagras'; return view('pedido/consultar', $data); } public function nuevo() { $data['mesas'] = $this->mesaModel->where('estado','libre')->findAll(); $data['productos'] = $this->productoModel->where('disponible',1)->findAll(); return view('pedido/registrar', $data); } }

Vistas asociadas en app/Views/pedido/:

  • consultar.php → Tabla de pedidos con estado y total
  • registrar.php → Formulario con selección de mesa y productos
  • ver.php → Detalle completo de un pedido específico
✓ CUMPLIMIENTO: Existen rutas propias, un controlador dedicado y tres vistas asociadas al módulo de pedidos.

10. Claves y relaciones correctamente definidas

10.1 Descripción

Las tablas deben contar con claves primarias (PK), claves foráneas (FK) y restricciones de integridad referencial que garanticen la consistencia de los datos.

10.2 Evidencia

Claves primarias: Cada tabla tiene un campo id_ con AUTO_INCREMENT PRIMARY KEY.

Claves foráneas y restricciones:

-- Pedido referencia a Mesa y Usuario ALTER TABLE pedido ADD CONSTRAINT fk_pedido_mesa FOREIGN KEY (id_mesa) REFERENCES mesa(id_mesa) ON DELETE RESTRICT ON UPDATE CASCADE; ALTER TABLE pedido ADD CONSTRAINT fk_pedido_usuario FOREIGN KEY (id_usuario) REFERENCES usuario(id_usuario) ON DELETE RESTRICT ON UPDATE CASCADE; -- Detalle referencia a Pedido y Producto ALTER TABLE detalle_pedido ADD CONSTRAINT fk_detalle_pedido FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido) ON DELETE CASCADE ON UPDATE CASCADE; ALTER TABLE detalle_pedido ADD CONSTRAINT fk_detalle_producto FOREIGN KEY (id_producto) REFERENCES producto(id_producto) ON DELETE RESTRICT ON UPDATE CASCADE; -- Pago y Preparacion (1:1 con Pedido) ALTER TABLE pago ADD CONSTRAINT fk_pago_pedido FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido) ON DELETE CASCADE ON UPDATE CASCADE; ALTER TABLE preparacion ADD CONSTRAINT fk_preparacion_pedido FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido) ON DELETE CASCADE ON UPDATE CASCADE;

Relaciones del modelo:

  • Usuario (1) → (N) Pedido
  • Mesa (1) → (N) Pedido
  • Pedido (1) → (N) Detalle_Pedido
  • Producto (1) → (N) Detalle_Pedido
  • Categoria (1) → (N) Producto
  • Pedido (1) → (1) Pago
  • Pedido (1) → (1) Preparacion
✓ CUMPLIMIENTO: Todas las tablas tienen PK, 6 restricciones FK con políticas ON DELETE/UPDATE definidas, y relaciones 1:N, N:M y 1:1 correctamente establecidas.

11. Modelo de CodeIgniter asociado a una entidad principal

11.1 Descripción

Debe existir al menos un Modelo de CodeIgniter 4 que represente una entidad principal del sistema, con configuración de tabla, clave primaria, campos permitidos y validaciones.

11.2 Evidencia: PedidoModel

La entidad principal del sistema es Pedido. Su modelo en CodeIgniter 4 es:

<?php namespace App\Models; use CodeIgniter\Model; class PedidoModel extends Model { protected $table = 'pedido'; protected $primaryKey = 'id_pedido'; protected $useAutoIncrement = true; protected $returnType = 'array'; protected $allowedFields = ['id_mesa','id_usuario','fecha','estado','total']; protected $useTimestamps = true; protected $createdField = 'created_at'; protected $updatedField = 'updated_at'; protected $validationRules = [ 'id_mesa' => 'required|is_natural_no_zero', 'id_usuario' => 'required|is_natural_no_zero', 'estado' => 'required|in_list[pendiente,en_preparacion,listo,entregado,cancelado]', 'total' => 'required|decimal', ]; public function getPedidosConDetalle() { return $this->select('pedido.*, mesa.numero as mesa_numero, usuario.nombre as mozo') ->join('mesa', 'mesa.id_mesa = pedido.id_mesa') ->join('usuario', 'usuario.id_usuario = pedido.id_usuario') ->orderBy('pedido.id_pedido', 'DESC') ->findAll(); } public function getPedidoPorId($id) { return $this->select('pedido.*, mesa.numero as mesa_numero, usuario.nombre as mozo') ->join('mesa', 'mesa.id_mesa = pedido.id_mesa') ->join('usuario', 'usuario.id_usuario = pedido.id_usuario') ->where('pedido.id_pedido', $id) ->first(); } }

Este modelo cumple con todos los estándares de CI4: tabla definida, clave primaria, auto-incremento, timestamps, validaciones integradas y métodos personalizados con JOIN.

✓ CUMPLIMIENTO: PedidoModel representa la entidad principal con configuración completa de CI4 y métodos de consulta avanzados.

12. Operación de registro funcionando

12.1 Descripción

El sistema debe permitir crear nuevos registros en la base de datos a través de un formulario web, con validación de datos y manejo de errores.

12.2 Evidencia: Registrar Pedido

Formulario (app/Views/pedido/registrar.php):

El mozo selecciona una mesa libre, elige productos del menú y especifica cantidades. El formulario envía por POST a /pedidos/registrar.

Procesamiento (PedidoController::registrar()):

public function registrar() { $db = \Config\Database::connect(); $db->transStart(); // Inicia transacción try { // 1. Calcular total del pedido $total = 0; foreach ($productos as $index => $idProducto) { $prod = $this->productoModel->find($idProducto); $cant = $cantidades[$index]; $total += $prod['precio'] * $cant; } // 2. Insertar pedido $this->pedidoModel->insert([ 'id_mesa' => $id_mesa, 'id_usuario' => $id_usuario, 'fecha' => date('Y-m-d H:i:s'), 'estado' => 'pendiente', 'total' => $total, ]); $idPedido = $this->pedidoModel->getInsertID(); // 3. Insertar detalles del pedido foreach ($productos as $index => $idProducto) { $prod = $this->productoModel->find($idProducto); $cant = $cantidades[$index]; $this->detalleModel->insert([ 'id_pedido' => $idPedido, 'id_producto' => $idProducto, 'cantidad' => $cant, 'precio_unitario' => $prod['precio'], 'subtotal' => $prod['precio'] * $cant, ]); } // 4. Actualizar mesa a ocupada $this->mesaModel->update($id_mesa, ['estado' => 'ocupada']); // 5. Crear preparación en cocina $this->preparacionModel->insert([ 'id_pedido' => $idPedido, 'estado' => 'pendiente', ]); $db->transComplete(); // Confirma todo return redirect()->to('/pedidos/ver/' . $idPedido) ->with('success', 'Pedido registrado correctamente.'); } catch (\Exception $e) { $db->transRollback(); // Revierte todo si hay error return redirect()->back()->with('error', $e->getMessage()); } }

Esta operación registra simultáneamente: el pedido, sus detalles, el cambio de estado de la mesa y la preparación en cocina, todo dentro de una transacción SQL que garantiza la integridad de los datos.

✓ CUMPLIMIENTO: Operación de registro completa con validación, transacciones y manejo de errores, verificable en el navegador.

13. Operación de consulta funcionando

13.1 Descripción

El sistema debe permitir visualizar registros almacenados, con filtros, búsquedas o listados que demuestren la correcta recuperación de datos.

13.2 Evidencia

Consulta 1: Listado de todos los pedidos

public function index() { $data['pedidos'] = $this->pedidoModel->getPedidosConDetalle(); return view('pedido/consultar', $data); }

Utiliza JOIN para mostrar el número de mesa y el nombre del mozo junto a cada pedido.

Consulta 2: Detalle de un pedido específico

public function ver($id = null) { $data['pedido'] = $this->pedidoModel->getPedidoPorId($id); $data['detalles'] = $this->detalleModel->getDetallePorPedido($id); return view('pedido/ver', $data); }

Muestra la información completa del pedido y la lista de productos con cantidades y subtotales.

Consulta 3: Catálogo de productos

public function index() { $data['productos'] = $this->productoModel ->select('producto.*, categoria.nombre as categoria_nombre') ->join('categoria', 'categoria.id_categoria = producto.id_categoria') ->findAll(); return view('producto/consultar', $data); }

Las tres consultas son accesibles mediante las URLs:

  • http://localhost:8080/pedidos → Lista de pedidos
  • http://localhost:8080/pedidos/ver/1 → Detalle del pedido #1
  • http://localhost:8080/productos → Catálogo de productos
✓ CUMPLIMIENTO: Tres operaciones de consulta funcionando con JOIN entre tablas, accesibles vía navegador.

14. Persistencia comprobada

14.1 Descripción

Se debe demostrar que los datos registrados se almacenan físicamente en la base de datos y persisten entre sesiones, incluso después de reiniciar el servidor.

14.2 Evidencia

Transacciones SQL: La operación de registro utiliza transStart() y transComplete(), lo que garantiza que todos los cambios se guardan de forma atómica. Si algo falla, se hace transRollback() y no queda basura en la base de datos.

Datos de prueba incluidos: El script SQL incluye un pedido de prueba con sus detalles:

Comprobación de persistencia: Al acceder a /pedidos después de reiniciar el servidor, el pedido #1 sigue visible con todos sus datos, demostrando que la información persiste en MySQL.

✓ CUMPLIMIENTO: Transacciones atómicas + datos de prueba verificables + persistencia demostrada tras reinicio del servidor.
